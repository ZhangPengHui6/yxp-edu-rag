1. **MinerU 凭据已切换（2026-10-24）**：原 `MINERU_TOKEN` 返回 401 `user token expired`；现已改用 OpenXLab `Access Key ID` / `Secret Access Key`，由 provider 自动换取 JWT 并续期。探测 `GET /extract-results/batch/probe-not-exist` 返回 200（`task not found`），说明鉴权已通过。

## 2. 范围与两条链路

### 2.1 生产链路：`apps/admin-api`

离线导入由管理端 API 触发，任务记录在 PostgreSQL，知识点/题目写入 MongoDB，片段与向量写入 Milvus 活动集合 `chunks_live`，发布时再构建版本化集合。学员端 `/v1` 检索服务不在本仓库。

```
管理端前端
   │  POST /admin/v1/ingestion/uploads         → 预签名上传地址
   │  PUT  <uploadUrl>                          → 文件进入 MinIO / 本地目录
   │  POST /admin/v1/ingestion/jobs             → PG 建任务 + 5 个步骤 + 派发
   ▼
[inline asyncio | Celery ingestion.run]
   │
   ├─ upload   读取源文件
   ├─ ocr      MinerU（优先）→ Qwen-VL（降级）
   ├─ split    Markdown → 带页码/标题路径的 chunk
   ├─ struct   知识点树 + 千问抽题 + 规则合并 + BGE-M3 向量
   ├─ quality  覆盖率统计 + 证据重排
   └─ persist  Mongo: knowledge_points / questions
               Milvus: chunks_live（片段 + dense/sparse 向量）
                                        │
                        审核通过 approved │
                                        ▼
   POST /admin/v1/publish/orders          → 发布单（draft）
   POST .../stage                         → 重建 chunks_<version> / questions_<version>
   POST .../commit                        → 别名原子切换 + approved → published
   POST .../rollback                      → 别名切回旧版本
```

### 2.2 旧工具：`tools/rag_ingest`（不属于生产链路）

早期用来验证“PDF → Markdown → chunk”的独立 CLI，产物只落 `docs/rag_data/processed/<doc_id>/`：

- 支持命令：`render` / `ocr` / `chunk` / `pipeline` / `status`；
- 输出：`pages.jsonl`、`ocr/book.md`、`chunks.jsonl`；
- **不写数据库、不生成题目/知识点、不做向量化**；
- 当前两份 PDF 均存在，但渲染页数、OCR、chunk 都是 0，说明从未完整跑过。

它适合做 OCR 质量对照，不应作为线上入库入口。

## 3. 任务模型与状态机

任务步骤固定为 5 个（`app/modules/ingestion/rules.py::STEP_DEFS`）：

| key | 前端标签 | 进度 |
| --- | --- | --- |
| `upload` | 文件上传 | 20% |
| `ocr` | 版面与 OCR 解析 | 40% |
| `split` | 题目切分 | 60% |
| `struct` | 结构化与公式 | 80% |
| `quality` | 质量检查 | 100% |

> 注意：`split` 的标签叫“题目切分”，实际实现是**按标题层级做通用文本切块**，不是先识别题目再切。题目识别发生在 `struct`。

任务状态：`pending → running → succeeded / failed / canceled`；`failed / canceled → pending`（仅重试）。

失败码：

| error_code | 触发条件 |
| --- | --- |
| `SOURCE_NOT_FOUND` | 对象存储中找不到 `source_uri` |
| `PROVIDER_UNAVAILABLE` | OCR 为空、切块为空、LLM 不可用、Milvus/BGE 失败等 |
| `PIPELINE_ERROR` | 其他未归类异常 |

LLM 结构化与证据重排失败**只降级该步骤**；OCR、切块、BGE-M3 向量化失败会让任务整体 `failed`。

> 测试环境默认 `OCR_PROVIDER=placeholder`，只按固定节奏推进状态机、不调用任何外部服务；生产配置为 `auto`，走下面的真实链路。两者共用同一套 PG 任务/步骤与前端状态。

任务成功后，`ingestion_job.stats` 会记录本次执行摘要：`pipeline`、`ocrProvider`、`pages`、`chunks`、`questions`、`knowledgePoints`、`llmStructuring`、`llmQuestions`、`llmKnowledgePoints`、`rerankedQuestions`、`rerankProvider`、`embeddedChunks`、`embeddedQuestions`、`embeddingProvider`、`finishedAt`。

## 4. 节点逐项说明

### N0 上传与任务创建

**职责**：分配对象存储 key，接收文件，创建 PG 任务与步骤，派发后台执行。

**代码**：
- `app/api/v1/ingestion.py`：`POST /uploads`、`POST /jobs`、`GET /jobs`、`GET /jobs/{id}`、`POST /jobs/{id}/retry`、`POST /jobs/{id}/cancel`；
- `app/modules/ingestion/service.py::create_presign / create_job / retry_job / cancel_job`；
- `app/infra/minio.py`：`MinioStorage` 或开发用 `LocalStorage`（HMAC 签名 + `PUT /admin/v1/ingestion/_dev/uploads/{key}` 落盘）；
- `app/infra/queue.py`：`TASK_MODE=inline` 用 `asyncio.create_task`；`celery` 调 `app.workers.parse_tasks.run_ingestion_job.delay()`。

**输入**：`filename`、`objectKey`、`sourceType`、`subject`、`stage`、`pages`、`sizeMb`，可选 `Idempotency-Key`。

**输出**：PG `ingestion_job`（`status=pending`，`current_step=upload`）+ 5 条 `ingestion_job_step`。

**实现状态**：✅ 完整。

**已知行为/缺口**：
- 幂等键只保证同租户同 key 返回已有任务，不校验上传内容；
- `object_key` 由客户端传入，服务端只按 key 读对象，**没有校验 key 是否属于当前租户**；
- 没有文件大小/扩展名/哈希校验；`sourceType` 只做枚举校验；
- 进程重启后不会扫描 `pending` 任务重新派发。
- `cancel` 只改 PG 状态，正在执行的 OCR/LLM 请求不会被打断；流水线只在**步骤边界**检查 `canceled`。

### N1 读取源文件

**职责**：按 `source_uri` 从 MinIO/本地存储取出字节。

**代码**：`modules/ingestion/graph/nodes/upload.py`；`infra/minio.py::get_bytes`。

**行为**：
- 无 `source_uri` → `FileNotFoundError`；
- 空字节 → `ProviderUnavailable("源文件为空")`；
- 成功后 step detail 记录 `已读取源文件（X MB）`。

**完成度**：✅。

### N2 OCR / 版面解析

**职责**：把 PDF/图片转成带页码锚点的 Markdown 与版面块。

**代码**：
- 工厂：`infra/providers/__init__.py::get_ocr_provider / get_ocr_fallback`；
- MinerU：`infra/providers/mineru.py`；
- Qwen-VL：`infra/providers/qwen_vl.py`；
- 降级：`modules/ingestion/graph/nodes/ocr.py::parse_with_fallback`。

**MinerU（首选）**：
1. **鉴权**：二选一
   - `MINERU_TOKEN`：直接作为 `Authorization: Bearer <token>`；
   - OpenXLab `MINERU_ACCESS_KEY_ID` + `MINERU_SECRET_ACCESS_KEY`：`POST {MINERU_AUTH_URL}/auth` 取 nonce/algorithm → 用 Secret Key 做 HMAC 签名得到 `d` → `POST /getJwt` 换 JWT；JWT 与 refresh_token 只缓存在进程内存，临期先用 `/refreshJwt` 续期，失败再用 AK/SK 重新登录。
2. `POST /file-urls/batch` 申请上传地址（`enable_formula=true`、`enable_table=true`、`model_version=vlm`）；
3. `PUT` 文件；
4. 轮询 `GET /extract-results/batch/{batch_id}`，间隔 `OCR_POLL_SECONDS=5`，超时 `OCR_TIMEOUT_SECONDS=1800`；
5. 下载结果 ZIP，安全解压（拒绝绝对路径与 `..`），读取 `*content_list.json`；
6. 转成 `<!-- page: N -->` + Markdown + `OcrBlock` 列表。

**Qwen-VL（降级）**：
1. PyMuPDF 按 `OCR_DPI=200` 逐页渲染为 JPEG；
2. 每页经 OpenAI 兼容 `/chat/completions` 送入视觉模型（当前 `QWEN_VL_MODEL=qwen/qwen3.7-flash`）；
3. 并发 `QWEN_VL_CONCURRENCY=4`，每页最多 4 次重试（指数退避 ≤8s），单请求 180s；
4. 拼成同样带页码锚点的 Markdown。

**降级条件**：主 provider 抛 `ProviderUnavailable`（含 HTTP 401/超时/解析失败）且另一个 provider 已配置。降级只尝试一次。

**完成度**：✅ 代码完整且鉴权已恢复：
- 2026-10-24 原 `MINERU_TOKEN` 曾返回 `401 A0211 user token expired`；
- 切换 OpenXLab AK/SK 后，`GET /extract-results/batch/probe-not-exist` 返回 **200**（`code=-60012 task not found or expire`），说明 JWT 已被 MinerU 接受；
- `auto` 仍保留 Qwen-VL 兜底；Qwen-VL 是逐页调用，成本和耗时高于 MinerU，且没有版面结构。

**支持的文件类型**：
- Qwen-VL：PDF、PNG/JPG/JPEG/WEBP；
- MinerU：PDF、PNG/JPG/JPEG（代码只给这 4 类映射 Content-Type）；
- **DOCX / ZIP 虽然在 API 枚举里，但两个 provider 都没有对应的解析分支**，Qwen-VL 会直接报“不支持的文件类型”。

### N3 切分

**职责**：把 OCR Markdown 切成检索单元，保留标题路径、页码范围和内容类型。

**代码**：`modules/ingestion/chunker.py`。

**规则**：
- 解析 `<!-- page: N -->` 锚点与 `#` 标题，维护“标题栈”；
- 公式块、表格块保持完整，尽量不跨块切断；
- 超长段落按中文句末标点（`。！？；`）二次切分；
- 目标长度 `CHUNK_SIZE=600`，重叠 `CHUNK_OVERLAP=80`（最多保留上一块最后一段）；
- 丢弃 `< 30` 字的碎片；
- 每个 chunk 产出：`content`、`heading_path`、`section_title`、`level`、`content_type`（text/table/formula）、`page_start/page_end`、`char_count`、`token_count`、`hash`。

**输出**：内存中的 `Chunk` 列表；落库时生成稳定 ID `chk_sha1(tenant|job|hash)[:20]`。

**完成度**：✅。

### N4 结构化：知识点、题目、片段

**职责**：从切分结果中抽取知识点树和题目，并把 chunk 关联到知识点。

**代码**：
- `modules/ingestion/extract.py`：规则层（标题树、题号标记、选项、答案、SimHash、知识点匹配）；
- `modules/ingestion/llm_extract.py`：千问结构化；
- `modules/ingestion/graph/nodes/struct.py`：合并 + 生成文档。

**知识点**：
1. 先按标题路径构造确定性知识点树（根节点为 `学段+学科`）；
2. 若 `LLM_STRUCTURING=true`，千问按批返回 `knowledge_points[]`（名称、父级、说明）；
3. `apply_llm_knowledge_points` 把 LLM 知识点合并进标题树，按规范化名称去重；
4. chunk 通过完整路径匹配知识点；题目通过知识点名称后缀匹配。

**题目**：
1. 规则抽取识别“例 / 例题 / 变式 / 练习”等题号标记，解析题干、选项、答案、解析；
2. 千问按批（`LLM_MAX_CHARS=8000`，并发 `LLM_CONCURRENCY=4`）返回 JSON，包含 `chunk` 编号、页码、题型、题干、选项、答案、解析、难度、知识点；
3. 输出非法 JSON 时追加一次“只返回 JSON”的修复调用；
4. 单个批次失败只跳过该批，全部失败则退回纯规则；
5. LLM 结果与规则结果按 `stem_key` 去重合并（LLM 优先）。

**LLM 调用细节**：
- 网关：`DASHSCOPE_BASE_URL=https://api.qnaigc.com/v1`（七牛云 OpenAI 兼容）；
- 模型：`LLM_DEFAULT_MODEL=qwen/qwen3.7-flash`；
- `enable_thinking=false`、`response_format=json_object`、`temperature=0.1`、`max_tokens=8192`；
- 题库字段默认：`review_status=reviewing`、`license_status=pending`、`quality_score=0.5`、`version=1`、`simhash`。

**完成度**：✅。规则层与 LLM 层都有，失败可降级。

**已知缺口**：
- 只做**任务内**去重，不跨任务查重；`simhash` 已写入但没有用于全库比对，同一本书重复导入会产生重复题目；
- LLM 抽取的题目答案/解析可能为空（提示词要求“原文没有则空字符串”），需要人工审核补齐；
- 知识点匹配依赖名称，LLM 改名后可能匹配不到。

### N5 向量化（BGE-M3）

**职责**：为 chunk 与题目生成 dense + sparse 向量，供 Milvus 检索。

**代码**：
- `infra/providers/bge.py`：`BgeM3EmbeddingProvider`；
- `modules/ingestion/graph/documents.py::embed_assets`；
- `infra/vectors.py`：Mongo/Milvus 稀疏向量格式转换。

**行为**：
- `EMBEDDING_PROVIDER=bge_m3` 时，在写库前一次性编码：
  - chunk `content` → `dense_vector`（1024 维，已归一化）、`sparse_vector`、`embedding_model`；
  - 题目 `stem` → `stem_vector` + `sparse_vector`；
  - 题目 `analysis` 或 `answer` 非空 → `solution_vector`；缺失时写 1024 维零向量；
- 模型懒加载，推理放线程池；`BGE_DEVICE=cpu`、`BGE_FP16=False`；
- 模型路径 `BGE_M3_PATH` 指向本地 ModelScope 快照，避免运行时联网；
- Mongo 的稀疏向量键必须为字符串（`{"123": 0.45}`），写 Milvus 时再转回整数键。

**完成度**：✅。实测：1024 维、模长 1.0、17 个稀疏权重，冷加载约 35s。

**数据补齐**：历史 Mongo 切片已在 2026-10-24 迁移到 Milvus `chunks_live`（101 条，均带 dense/sparse）；若仍有缺向量的片段，发布 `stage` 会自动补算。

### N6 质量检查与证据重排

**职责**：统计质量指标，为每道题找最相关的源片段，写 `evidence_chunk_ids` / `evidence_score`。

**代码**：`modules/ingestion/evidence.py`、`modules/ingestion/graph/nodes/quality.py`、`infra/providers/qwen.py`。

**行为**：
- 统计：有效片段比例（≥80 字）、答案覆盖率；
- 候选片段：同页优先，其次按题干与片段前 600 字的字符二元组重合度排序，取 `RERANK_CANDIDATES=6` 个；
- 重排：默认 `RERANK_PROVIDER=qwen_llm`，用千问聊天模型给候选打分（七牛云没有原生 rerank 接口）；
- 每题最多取 `RERANK_TOP_EVIDENCE=2` 个片段；只处理前 `RERANK_MAX_QUESTIONS=50` 道题；
- 重排失败只记 warning，不影响任务成功。

**完成度**：⚠️ 功能已实现，但**只是增强项**：
- 没有任何阈值会让任务失败或标记题目不合格；
- `quality_score` 仍是固定的 0.5，没有根据覆盖率/重排分回写；
- 超过 50 道的部分没有证据。

### N7 落库（Milvus + MongoDB）

**职责**：把知识点、题目写入 Mongo，把 chunk（含向量）写入 Milvus，并刷新知识点计数。

**代码**：`modules/ingestion/graph/persistence.py::clear_job_assets / write_knowledge_points / write_chunks / write_questions / refresh_knowledge_counts`；chunk 读写统一经 `app/infra/chunk_store.py`。

**行为**：
- 写入前按 `tenant_id + job_id` 删除旧 chunk（Milvus）与 question（Mongo），保证重试幂等；
- 知识点 `update_one(upsert)`，保留首次 `created_at`，刷新 `updated_at`；
- chunk 通过 `MilvusChunkStore.upsert` 写入活动集合 `chunks_live`（`MILVUS_CHUNKS_COLLECTION`），question 用 `replace_one(upsert)` 写 Mongo；
- 聚合刷新知识点的 `paragraph_count`（按 `ARRAY_CONTAINS(kp_ids, …)` 统计 Milvus）/ `question_count`（Mongo）；
- 集合：`knowledge_points`、`questions`（Mongo）、`chunks_live`（Milvus）；Mongo 索引见 `infra/mongo.py::init_indexes`。

**完成度**：✅。

**注意**：`clear_job_assets` 只清理同一 job 的产物；如果同一本书被创建成两个 job，会产生两套 `book_id`（`book_<job_id>`）和重复内容。

### N8 发布索引（stage / commit / rollback）

**职责**：把 Milvus 活动集合中的 chunk 与 Mongo 题目物化为版本化 Milvus 集合，通过别名原子切换对外生效。

**代码**：
- `app/modules/publish/service.py`：`create_order / stage_order / commit_order / rollback_order`；
- `app/modules/publish/indexer.py`：`build_version_index`；
- `app/infra/milvus.py`：集合/别名适配器。

**create（draft）**：
- 版本号 `%Y%m%d_%H%M%S`；
- 统计 chunk 数、可发布题目数、近 30 天变化；
- 生成检查项快照：引用完整性、向量完整性、别名可用性、发布前评测。

**stage**：
1. 读取该租户 `chunks_live` 中的**全部 chunk** + Mongo 中 **`approved` / `published` 题目**；
2. 老 chunk 缺 `subject/stage` 时，通过 `knowledge_point_ids` 回填并写回 Milvus；
3. 缺失向量用 BGE-M3 补算并写回 `chunks_live`；
4. 删除并重建 `chunks_<version>`、`questions_<version>`：
   - chunk：`chunk_id` 主键，`tenant_id/job_id/book_id/book_title/edition/subject/stage/grade/kp_ids/content_type/content/location/page_start/page_end/dense_vector/sparse_vector`；
   - question：`question_id` 主键，学科/学段/年级/教材/章节/kp_ids/题型/难度/`review_status`/`stem_vector`/`solution_vector`/`sparse_vector`；
   - dense 用 HNSW COSINE（M=16，efConstruction=200），sparse 用 `SPARSE_INVERTED_INDEX` IP；
5. 调 `stage` 记录集合行数；只对“引用完整性”“别名可用性”硬失败，评测不通过只记录。

**commit**：
1. 重新执行全部检查，**评测未通过会阻断提交**（`EVAL_RECALL_THRESHOLD=0.85`）；
2. `chunks_active`、`questions_active` 依次指向新集合；
3. PG 发布单置 `published`；
4. Mongo `approved` 题目 → `published`，`reviewing` 教材 → `published`。

**rollback**：只把别名指回旧版本，不回滚 Mongo 状态。

**本次修正（2026-10-24）**：
- 原实现只索引 `review_status=published` 的题目，但 `approved → published` 发生在 `commit` 之后。结果是**本次发布中新审核通过的题目不会进入本次索引**，要等下一版。已改为索引 `approved + published`，Milvus 行统一写 `review_status=published`；
- 单测相应增加 `approved` 用例，当前 **39 passed**，ruff / mypy 无告警。

**剩余限制**：
- stage 之后、commit 之前新审核通过的题目，会在 commit 时被一并改为 `published`，但不在本次索引里，要等下个版本；
- `license_status=restricted` 的题目目前没有被排除（按“暂不考虑合规”处理）；
- 活动别名当前指向空集合（见 §6）。

## 7. 完成度矩阵与整改建议

### P0（阻塞“可完整跑通”）

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| ~~MinerU 凭据~~ | 原 token 过期 | ✅ 已切换 OpenXLab AK/SK，自动换 JWT |
| pending/running 任务不恢复 | 重启后任务永久卡住，`running` 无法重试 | 启动时把 `running` 标记为 `failed`（或重新派发 `pending`）；放开 `running` 的 retry |
| 活动索引为空（别名仍指旧集合） | 学员端检索为空 | 已有 `chunks_live` 数据，执行一次 stage/commit 即可切换别名 |

### P1（影响质量/可运维性）

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| Celery 模式未验证 | 生产无法水平扩展任务 | 起 Redis + worker，跑一次 `TASK_MODE=celery` 任务 |
| DOCX/ZIP 枚举可用但 provider 不支持 | 用户上传后任务失败 | 建任务时按 provider 能力校验，或先做 DOCX→PDF、ZIP 解包 |
| 取消不打断外部调用 | 用户终止后仍在计费/占资源 | 在 OCR/LLM 调用间增加取消检查，或引入任务级取消令牌 |
| 无跨任务去重 | 重复导入产生重复题 | 用 `simhash` 在全库做近重复查询后再写入 |
| `object_key` 未校验租户 | 可读取其他租户对象 | key 加租户前缀并在读取时校验 |
| 质量步骤不拦截 | 低质量数据直接进入审核 | 设最小答案覆盖率/证据命中率，未达标标记 `needs_review` |

### P2（发布/数据一致性）

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| stage 后新审批题目不在本次索引 | 状态已发布但检索不到，直到下版 | commit 前重新 stage，或仅提升本次索引内的题目 |
| rollback 不回滚 Mongo 状态 | 管理端显示已发布、检索走旧索引 | 按发布快照恢复，或改为单向发布视图 |
