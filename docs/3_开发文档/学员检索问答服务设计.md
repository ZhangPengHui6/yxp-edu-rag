# 学员检索问答服务设计（`/v1`）

> 设计日期：2026-10-26
> 代码基线：`apps/kb-api`（新增），复用 `apps/admin-api` 的 Provider / Milvus / Mongo 适配层
> 目标：让学员侧能基于已发布教材做“检索 → 重排 → 有引用生成”，先交付最小可验证版本
> 验证环境：远程生产栈（VMware Ubuntu 主机上的 Milvus / Mongo / MinIO，地址已脱敏）+ 七牛千问网关 + 本地 BGE-M3

---

## 1. 边界与结论

| 项 | 结论 |
| --- | --- |
| 服务进程 | 独立 FastAPI，端口 `8001`，前缀 `/v1`，与管理端 `8000` 的 `/admin/v1` 并存 |
| 数据依赖 | 只读 Milvus 别名 `chunks_active` / `questions_active`；读写 Mongo `answer_records`；**不连 PostgreSQL** |
| 代码复用 | 通过 `kb_app/__init__.py` 把 `apps/admin-api` 注入 `sys.path`，复用 `app.core.config`、`app.infra.providers`、`app.infra.mongo` |
| 编排 | LangGraph `StateGraph`：`START → confirm → retrieve → rrf → rerank → generate → END` |
| 流式 | 同一张图去掉 `generate` 节点，生成阶段由 HTTP 层直接向 LLM 发起流式请求并转发 SSE |
| 当前数据 | `chunks_active` 305 行（教材片段，含 `content` / `book_title`）；`questions_active` 30 行（种子练习题，含题干 / 选项 / 答案 / 解析） |

为什么独立成服务而不是挂在管理端：管理端的生命周期跟着导入 / 发布任务走，依赖 PG 与 Alembic；
学员侧是高 QPS、只读、需要独立扩缩容与独立 API Key 配额，放在同一进程会互相拖累。
此外管理端已经声明“学员 `/v1` 不在本仓库”，本服务即该声明的落地。

## 2. 拓扑

```
                    ┌──────────────────────────────┐
  学员前端 / 小程序 ─▶│  kb-api  :8001  /v1          │
                    │  FastAPI + LangGraph         │
                    └───┬──────────┬──────────┬────┘
                        │          │          │
              BGE-M3 查询向量   四路检索     生成 / 重排
                        │          │          │
                        ▼          ▼          ▼
                 本地 FlagEmbedding  Milvus  千问 OpenAI 兼容网关
                 (1024 dense+sparse) 别名      qwen3.7-flash
                                    │
                              chunks_active → chunks_<version>
                              questions_active → questions_<version>
                        │
                        ▼
                  Mongo: answer_records（审计）
```

发布链路仍然是管理端的两阶段发布：stage 建版本化集合，commit 切别名。学员侧只认别名，
所以发布切换对在线服务是原子的，不需要重启。

## 3. 节点编排

### 3.1 图

```
START
  │
  ▼
confirm ── 归一化问题、校验长度、关键词补 subject/stage
  │
  ▼
retrieve ── BGE-M3 编码 → 教材 dense/sparse ∥ 题目 dense/sparse → 各 top_k
  │
  ▼
rrf ── 1/(k+rank) 四路融合（题目按 KB_QUESTION_WEIGHT 加权），截断到 fused_top_n（题目保底 KB_QUESTION_QUOTA 个槽位）
  │
  ▼
rerank ── 交叉编码打分（当前为 qwen_llm），失败退化为 RRF 顺序
  │
  ├── /v1/chat ──────────► generate ── 组装编号上下文 → LLM → 引用 / 置信度 → END
  └── /v1/chat/stream ───► END（HTTP 层用同一上下文流式生成）
```

两张图通过 `_build(with_generate: bool)` 生成，`lru_cache` 缓存编译结果。
流式路径之所以拆开：LangGraph 节点返回值是整体状态，无法边生成边 yield；
把生成放在 HTTP 层的 `async generator` 里，才能做到“先推 meta / citation，再逐个 delta”。

### 3.2 节点契约

| 节点 | 输入（读） | 输出（写） | 失败策略 |
| --- | --- | --- | --- |
| `confirm` | `query`, `messages`, `subject`, `stage` | `query`, `rewritten_query`, `subject`, `stage`, `timings.confirm` | 空 / 超长直接 `AppError(INVALID_ARGUMENT)` → 400，不消耗 embedding |
| `retrieve` | `rewritten_query`, `tenant_id`, 过滤字段, `top_k` | `dense_hits`, `sparse_hits`, `question_dense_hits`, `question_sparse_hits`, `timings.retrieve` | Milvus / Provider 异常向上抛 → 503，不返回空答案伪装成功 |
| `rrf` | 四路命中 | `fused_hits`（含各路 rank/score，题目保底配额）, `timings.rrf` | 纯计算，无外部依赖 |
| `rerank` | `fused_hits`（截断后的正文） | `reranked_hits`, `rerank_provider`, `timings.rerank` | 任意异常 / 未配置 → RRF 顺序 + `rrf-fallback`，不影响可用性 |
| `generate` | `reranked_hits`, 历史, prompt | `answer`, `citations`, `confidence`, `model`, `timings.generate` | 无命中返回固定拒答文案；Provider 异常向上抛 → 503 |

### 3.3 并发与顺序

- `retrieve` 内教材 dense/sparse 与题目 dense/sparse 四路用 `asyncio.gather` 并发，Milvus 调用通过 `run_in_threadpool` 下放。
- `confirm → retrieve → rrf → rerank` 必须串行；`generate` 依赖 `rerank` 的最终序。
- BGE-M3 在进程内单例缓存（`kb_app/infra/retrieval.py::_embedding`），首次请求加载权重，
  之后所有请求复用；编码本身有 `threading.Lock`，同进程内不会并发跑两批推理。

## 4. 状态字段（`QueryState`）

`TypedDict(total=False)`，节点返回局部字典，LangGraph 合并。

| 字段 | 类型 | 写入 | 说明 |
| --- | --- | --- | --- |
| `request_id` | `str` | HTTP 层 | `req_<ULID>`，与响应头 `X-Request-Id` 一致 |
| `query` / `rewritten_query` | `str` | confirm | 当前版本二者相同；预留改写 / 指代消解 |
| `messages` | `list[{role, content}]` | HTTP 层 | 最近对话，`system` 被丢弃 |
| `tenant_id` | `str` | HTTP 层 | 缺省 `KB_DEFAULT_TENANT` |
| `subject` / `stage` / `grade` / `book_id` | `str` | HTTP 层 / confirm | 显式传入优先，否则按关键词推断学科 / 学段 |
| `top_k` | `int` | HTTP 层 | 单路检索条数 |
| `dense_hits` / `sparse_hits` | `list[dict]` | retrieve | 教材原始命中（`source=chunk`），保留原始 `score` |
| `question_dense_hits` / `question_sparse_hits` | `list[dict]` | retrieve | 题目原始命中（`source=question`），`content` 已拼成题干 / 选项 / 答案 / 解析 |
| `fused_hits` | `list[dict]` | rrf | 追加 `rrf_score`、`{channel}_rank`、`{channel}_score` |
| `reranked_hits` | `list[dict]` | rerank | 追加 `rerank_score`，顺序即最终顺序 |
| `rerank_provider` | `str` | rerank | 实际生效的 provider，或 `rrf-fallback` |
| `citations` | `list[dict]` | generate | 对外引用结构（见 §5.1） |
| `answer` | `str` | generate | 非流式路径的完整回答 |
| `confidence` | `high\|medium\|low` | generate | 见 §6.3 |
| `model` | `str` | generate | 实际模型名 |
| `timings` | `dict[str, int]` | 各节点 | 毫秒，键为节点名 |
| `error` | `str` | 预留 | 节点内可恢复错误，当前未使用 |

## 5. 接口契约

### 5.1 `POST /v1/chat`

请求：

```json
{
  "query": "圆锥的体积公式是什么？",
  "messages": [{"role": "user", "content": "上一轮问题"}],
  "tenant_id": "tnt_yxp",
  "subject": "数学",
  "stage": "high",
  "grade": "高一",
  "book_id": "",
  "top_k": 20
}
```

- `query` 为空时回退到最后一条 `user` 消息；两者都为空 → 400。
- `tenant_id` 缺省取 `KB_DEFAULT_TENANT`。
- `subject` / `stage` 缺省时从问题关键词推断（数学 / 物理 / …，小学 / 初中 / 高中）。

响应 `200`：

| 字段 | 说明 |
| --- | --- |
| `request_id` | 请求追踪号 |
| `answer` | 中文回答，引用处带 `[n]` |
| `citations[]` | `citation_id`（`c1`…）、`source`（`chunk` / `question`）、`chunk_id`、`question_id`、`book_id`、`book_title`、`subject`、`stage`、`question_type`、`difficulty`、`page_start`、`page_end`、`score`、`quote`（正文截断 1200 字） |
| `confidence` | `high` / `medium` / `low` |
| `model` | 生成模型 |
| `rewritten_query` | 实际用于检索的问题 |
| `retrieval` | `{dense, sparse, questions, fused, reranked}` 条数 |
| `timings_ms` | 各节点毫秒 |
| `latency_ms` | 端到端毫秒 |

### 5.2 `POST /v1/chat/stream`

`text/event-stream`，事件顺序固定：

| 事件 | 时机 | 载荷 |
| --- | --- | --- |
| `meta` | 检索完成后、生成前 | `request_id`、`scene`、`rewritten_query`、`retrieval`、`rerank_provider` |
| `citation` | 每条引用一次 | 与 §5.1 `citations[]` 单项相同 |
| `delta` | 模型每段输出 | `{"delta": "..."}` |
| `done` | 正常结束 | `request_id`、`latency_ms`、`model`、`confidence`、`retrieval` |
| `error` | 上游失败 | `code`（如 `MODEL_UNAVAILABLE`）、`message`、`retryable`、`request_id` |

约定：

- 无命中时先发 `meta` / 不引用，再发一条固定拒答的 `delta`，最后 `done`，前端无需特判。
- `error` 出现在已发部分 `delta` 之后时，前端保留已渲染内容并提示可重试。
- 响应头 `Cache-Control: no-cache`、`X-Accel-Buffering: no`，避免反向代理缓冲。

### 5.3 `GET /v1/health`

返回别名解析结果与依赖状态，用于发布切换后的自检：

```json
{
  "status": "ok",
  "tenant": "tnt_yxp",
  "chunks_alias": "chunks_active",
  "chunks_alias_collection": "chunks_20261026_030621",
  "chunks": 305,
  "questions_alias": "questions_active",
  "questions": 30,
  "embedding_provider": "bge_m3",
  "llm_configured": true,
  "mongo_ok": true
}
```

别名解析不到集合时 `status=degraded`，但进程仍启动，便于在发布前部署。

### 5.4 错误模型

沿用管理端 `AppError` 的字段，但只返回扁平结构（学员端不消费管理端信封）：

```json
{"code": "INVALID_ARGUMENT", "message": "问题不能为空", "details": {}, "request_id": "req_..."}
```

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 / 422 | `INVALID_ARGUMENT` | 空问题、超长、请求体校验失败 |
| 401 | `UNAUTHORIZED` | `X-API-Key` 缺失或错误 |
| 404 | `NOT_FOUND` | 路径不存在 |
| 503 | `MODEL_UNAVAILABLE` / `PROVIDER_UNAVAILABLE` | LLM 429/超时、Milvus 不可用、Embedding 未配置 |
| 500 | `INTERNAL` | 未预期异常（日志落 `kb_unhandled_error`） |

## 6. 检索与生成策略

### 6.1 过滤条件

`tenant_id` 必带，其余（`subject` / `stage` / `grade` / `book_id`）非空才拼接：

```text
tenant_id == "tnt_yxp" and subject == "数学" and stage == "high"
```

字符串统一做引号 / 反斜杠转义（`_quote`），避免 Milvus 表达式注入。
注意：当前片段文档带 `stage` 但筛选值来自关键词推断，若推断错误会过滤掉正确教材，
因此推断只在请求未显式传参时生效，且 API 调用方应尽量传显式过滤条件。

### 6.2 融合与重排

- RRF：`score = Σ weight / (60 + rank)`，教材两路 `weight=1.0`，题目两路 `weight=KB_QUESTION_WEIGHT`（默认 1.0）；
  同一 `chunk_id` / `question_id` 合并（键为 `chunk:<id>` / `question:<id>`）。
- 融合后取 `fused_top_n=10` 交给 rerank，返回 `rerank_top_n=5`。
- 题目配额：融合结果里最多先取 `KB_QUESTION_QUOTA=3` 道题，其余槽位按全局 RRF 顺序补教材；
  不足时再用剩余候选补满。这样既不会让 305 条教材挤掉精准匹配的题目，也不会让弱相关题目占满窗口。
- rerank 输入是把候选正文截断到 1200 字后交给 `qwen_llm` 打分；返回的 `(index, score)`
  直接映射回候选列表，`score` 即引用展示分。
- `rerank_provider` 为 `rrf-fallback` 时，`rerank_score` 取 RRF 分值，置信度最高只给 `medium`。

### 6.3 提示词与置信度

系统提示词（`kb_app/query/nodes/generate.py::SYSTEM_PROMPT`）：

1. 只能依据【教材与题目资料】回答，不得编造内容 / 页码 / 出处；
2. 引用处标注 `[n]`；
3. 练习题及其答案只能作为参考，必须说清推理过程；
4. 资料不足时明确说明缺什么，并给出可追问方向；
5. 中文、先结论后推导、公式清晰。

上下文按来源分别编号：教材片段为 `[1]《书名》（数学 · high · 第 51 页）`，
练习题为 `[2] 练习题（数学 · high · 难度 medium）`，正文保留题干 / 选项 / 答案 / 解析，
总长受 `KB_MAX_CONTEXT_CHARS` 限制。
置信度规则：

| 条件 | confidence |
| --- | --- |
| 无命中 | `low` |
| rerank 退化（`rrf-fallback`） | `medium` |
| rerank 首条 `score ≥ 0.7` | `high` |
| `0.4 ≤ score < 0.7` | `medium` |
| 其余 | `low` |

注意这是**排序信号**的阈值，不是校准过的概率；后续接入评测集后应改为按指标调参。

## 7. 审计与可观测性

- 每次问答（含流式）写 Mongo `answer_records`：`request_id`、`tenant_id`、`student_id`（预留）、
  `scene`、`query`、`answer`、`citations`、`confidence`、`latency_ms`、`model`、`retrieval`、`created_at`。
- 写失败只打 `answer_record_failed` 警告，不影响响应；`KB_RECORD_ANSWERS=false` 可关闭。
- 日志为 structlog JSON，事件名：`kb_api_started`、`kb_api_key_missing`、`rerank_failed`、
  `kb_stream_failed`、`answer_record_failed`、`kb_unhandled_error`。
- 响应头 `X-Request-Id` 回填请求自带值或新生成，便于把前端问题与日志、审计记录对齐。

| --- | --- |

## 9. 已知缺口与演进

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| P0 | 题目为种子数据 | `questions_active` 当前 30 道 `source=seed` 练习题；正式题库发布后需删除种子题并重切别名 |
| P0 | 题目配额未调参 | `KB_QUESTION_WEIGHT=1.0` / `KB_QUESTION_QUOTA=3` 是启发式取值；需用评测集同时观察教材与题目的命中率 |
| P0 | 无相关性阈值 | 离题问题仍会带低分片段进 prompt；建议 rerank 后按 `min_score` 截断，并区分“无命中”与“低置信” |
| P1 | 生成与重排共用网关配额 | 429 时整次请求 503；需要客户端重试退避、并发闸门，或把 rerank 换成独立 rerank 服务 |
| P1 | 首次请求加载 BGE-M3 数秒 | 生产可改为启动预热（lifespan 里 `_embedding()`），或独立 embedding 服务 |
| P1 | CPU 推理时延高 | `BGE_DEVICE=cuda` + `use_fp16` 可显著降低 retrieve 时延；评测前先定硬件基线 |
| P2 | API Key 无租户绑定 / 配额 | 目前单 key，后续接 `api_keys` 集合并按租户限流 |
| P2 | 会话与学情未落库 | `student_id` 已预留；多轮改写、指代消解尚未接入 |
| P2 | 未接评测 | 可用现有 `modules/evaluation` 的召回指标做离线回归，再作为发布门禁 |

## 10. 前端聊天窗口（`yxp_rag_front`）

管理端控制台新增 `/chat` 页面，直接消费本服务的 SSE 接口：

| 项 | 实现 |
| --- | --- |
| 路由 / 菜单 | `src/views/ChatView.vue`，路由 `/chat`（`dashboard.view`），“学员服务 → 学员问答” |
| 鉴权与地址 | `src/api/kb.ts`：`VITE_KB_BASE`（默认 `/v1`）、可选 `VITE_KB_API_KEY` → `X-API-Key` |
| 开发代理 | `vite.config.ts` 把 `/v1` 转发到 `VITE_KB_PROXY_TARGET`（默认 `http://127.0.0.1:8001`），并关闭代理缓冲 |
| 流式渲染 | `fetch` + `ReadableStream` 手工解析 `event:` / `data:`，按 `meta / citation / delta / done / error` 分发 |
| 布局 | 左侧对话区（消息流 + 输入框），右侧“引用与检索”面板（检索词、四路统计、引用卡片） |
| 交互 | 回答中的 `[n]` 可点击定位引用卡片；支持学科 / 学段过滤、示例问题、停止生成、复制回答、清空对话 |
| 状态 | 顶部展示 `/v1/health` 的片段数 / 题数；连接失败时显示告警并可重试 |

请求体把当前会话最近 6 条消息作为 `messages` 传入，服务端再按 `KB_HISTORY_TURNS` 截断，
用于多轮指代。前端不做答案缓存，引用与统计全部来自服务端事件。
